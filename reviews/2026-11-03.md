# Weekly review: 2026-11-03

## Could change a result
- **Self-consistency maj@5 vs greedy (gsm8k-selfconsistency)**: the lab output shows `acc=0.720` on the paired 100 questions against greedy's 68%. That is +4 points, which clears the pre-registered ≥+3 bar. Four things make this pass weak or uncertain:
  1. **Noise.** +4 is inside one SE (~4.7 points unpaired), which the README itself acknowledges. Whether this is a pass or noise depends entirely on the discordant counts (greedy-wrong→vote-right vs greedy-right→vote-wrong). Those are not yet reported. With n=100, a split like 10 vs 6 would not be significant.
  2. **Inconsistent baselines.** The agent's hand-corrected greedy figure is ~69%. If that is used as the baseline while SC stays uncorrected, the margin falls to +3, exactly on the threshold. Both arms must use the same scorer, both raw or both hand-checked.
  3. **Scorer affects voting.** Only 11% of outputs use `####`, so most votes come from the last-number fallback. Mis-extraction like idx 1117 (459 instead of 9) can create or break majorities. The SC arm needs the same manual check of wrong answers that greedy got.
  4. **What `acc` measures.** The log does not say whether `acc` in the k=5 run is maj@5 or something else, such as the first sample. This should be confirmed from the jsonl.

  What would settle it: report paired discordant counts and a McNemar/sign-test p-value, score both arms with the same scorer, and confirm the metric. If p is not small, the honest label is "met the pre-registered threshold, but not distinguishable from noise." It should not be presented as "self-consistency helps."
- **Greedy baseline "confirmatory" label (gsm8k-baseline)**: the README's "Prediction (written before running)" section was first committed in bcd79ec (22:08), the same commit as `results_qwen1.5b_greedy_n100.jsonl` and the Results section. Commit history cannot show that the prediction came first. The session actions list `write_file README.md` before the run, which is suggestive, but the README may have been rewritten afterwards. The 68% number itself is fine. The confirmatory label is unverifiable. The predicted range (55–70%) is also wide enough that a pass carries little information.
- **"True accuracy is about 69%"**: only the 32 wrong answers were hand-checked for scorer errors. The 68 "correct" answers were not checked for false credit from the last-number fallback, which drives 89% of scoring. The correction can therefore only move the score up. This one-sided check is used to imply the scorer error is "≈1%" and "rare". Settle it by checking the correct-scored outputs that lack `####`/`\boxed`, or by reporting only the raw 68%.
